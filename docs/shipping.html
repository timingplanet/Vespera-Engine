Standalone games

Build through the editor

Normal developers should use Build → Build Game…. The PowerShell export script remains useful for source-checkout automation, but it is not the required player workflow.

Build Game

The Build Game window offers Build, Build & Run, package preflight/status, recent output, and Open Output Folder. Packaging verifies required project, runtime, managed, and portable-.NET closure before reporting success.

Managed deployment

Projects may use framework-dependent managed deployment or a portable private .NET runtime. Portable packages include the runtime closure beside the executable; distribute the whole output folder, not only the .exe.

Release behavior

Packaged shared-player Release games use the Windows GUI subsystem, so end users do not receive an unwanted console window. Development/source-tree runs remain diagnostics-friendly.

Crash and runtime logs

Shared-player games mirror diagnostics to:

%LOCALAPPDATA%\Vespera\Logs\<game>.log

Top-level fatal exceptions and emergency Windows exception markers are written there when possible.

The final 1.0 release gate exercises fresh starter creation, Release packaging, portable .NET closure, standalone launch/log checks, and ordinary sample exports.
